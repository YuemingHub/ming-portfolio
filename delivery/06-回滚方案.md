# 回滚方案

- 编写日期：2026-11-02
- 适用对象：`ymai.me` 根路径作品集 + `/gui/` Self Space（2026-11-03 切换后）；`/ming/` 子路径方案保留为历史回滚点
- 当前状态：方案与本地演练完成；生产部署已完成（2026-11-03），生产回滚未触发
- 原则：先恢复服务，再查原因；不删除任何发布目录或历史文件

## 1. 触发条件

出现以下任一情况立即回滚，不先做“再调一下试试”：

| # | 现象 |
| --- | --- |
| 1 | `nginx -t` 失败，或 reload 后 `/ming/` 仍返回 Self Space fallback |
| 2 | 8 条页面中任一条 404，或深链、尾斜杠出现循环跳转 |
| 3 | CSS、JS、图片未加载，或 MIME 类型错误 |
| 4 | 根站 `/` 的响应字节与部署前基线不一致 |
| 5 | 已记录的 `/gui/_next/` 资源响应字节与基线不一致 |
| 6 | nginx error log 出现与本次规则相关的 5xx 或 rewrite 循环 |
| 7 | 其他站点的路由被 `/ming/` 规则影响 |

只有 `/ming/` 自身异常、根站与 `/gui/` 正常时，仍是回滚理由；不要因为“只影响子路径”而延迟。

## 2. 回滚等级

| 等级 | 动作 | 影响面 | 目标时间 |
| --- | --- | --- | --- |
| R1 | `current` 指回上一个 release | 仅 `/ming/` 内容 | 1 分钟内 |
| R2 | 从 server 块移除 `include`，reload | `/ming/` 回到根站 fallback | 3 分钟内 |
| R3 | 恢复部署前 nginx 配置备份，reload | 恢复到部署前整体状态 | 5 分钟内 |

优先级：先判断问题在“内容”还是“规则”。

- 新版内容有问题、规则正常 → R1。
- 规则本身导致异常 → R2。
- 配置叠加导致无法定位 → R3。

## 3. R1：切回上一个 release

```bash
ls -l <PORTFOLIO_PARENT>/current
ls -1 <PORTFOLIO_PARENT>/releases/
```

确认上一个 release 目录存在且完整，然后：

```bash
ln -s "releases/<PREVIOUS_RELEASE_ID>" <PORTFOLIO_PARENT>/current.next
mv -Tf <PORTFOLIO_PARENT>/current.next <PORTFOLIO_PARENT>/current
```

无需 reload nginx：软链接在每次请求时解析（除非配置了缓存）。验证：

```bash
curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' https://ymai.me/ming/
curl -sS https://ymai.me/ming/ | sha256sum
```

若 `current` 原本不存在（首次发布），R1 不适用，直接 R2。

不删除新 release；保留现场用于排查。

## 4. R2：移除 `/ming/` 规则

1. 从 `ymai.me` 的 HTTPS server 块中删除 `include <SNIPPET_PATH>;` 这一行。
2. 保留片段文件，不删除，便于复查。
3. 验证并 reload：

```bash
nginx -t
systemctl reload nginx    # 或实际 reload 命令
```

4. 验证 `/ming/` 已回到部署前行为：

```bash
curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' https://ymai.me/ming/
curl -sS https://ymai.me/ming/ | sha256sum
```

应与部署前基线一致（部署前 `/ming/` 是 Self Space 的 SPA fallback）。

## 5. R3：恢复配置备份

仅当 R1、R2 无法恢复，或无法判断哪条规则引起问题时：

```bash
# 先保留当前现场
cp -a /etc/nginx <BACKUP_DIR>/nginx-failed-<timestamp>

# 恢复部署前备份
rsync -a --delete <BACKUP_DIR>/nginx-backup/ /etc/nginx/

nginx -t
systemctl reload nginx
```

`rsync --delete` 只作用于 nginx 配置目录的恢复，不删除站点文件、发布目录或历史资产。执行前必须确认 `<BACKUP_DIR>/nginx-backup` 是本次部署前生成的完整备份。

如果 `nginx -t` 仍失败，不要反复 reload；保留现场并升级到 Owner / 运维负责人。

## 6. 回滚后验证

按顺序执行：

```bash
# 1. 根站与 /ming/ 的字节；回滚后的预期是部署前基线里的 ming.html
node deploy/verify.mjs post \
  --base https://ymai.me \
  --prefix /ming \
  --baseline <BACKUP_DIR>/baseline \
  --expect-index <BACKUP_DIR>/baseline/ming.html

# 2. 若基线记录了 /gui/_next/ 资源，确认其字节未变
#    verify.mjs 会自动对比；无记录时显示 SKIP

# 3. 浏览器渲染
cd site
node tests/render-check.mjs --base https://ymai.me --prefix /ming
```

注意：回滚到部署前状态后，`render-check.mjs` 对 8 条路由的作品集检查会失败，因为 `/ming/` 又回到 Self Space fallback。此时应改用：

- 根站 `/` 可正常打开；
- `/ming/` 的字节与部署前基线一致；
- `/gui/` 与 `/_next/` 资源与基线一致；
- 浏览器无新增 console error。

不要把“回滚后作品集检查失败”误判为回滚失败。判据是“回到基线”，不是“新功能仍然可用”。

## 7. 证据保留

## 11. 本次部署的实际回滚点（2026-11-03）

本次是 `/ming/` 的首次独立部署，部署前没有 `current` 软链接；因此最快的回滚不是切版本，而是**移除 `include` 并 reload**，让 `/ming/` 回到部署前的 Self Space fallback。

### 11.1 最小回滚（R2）

```bash
# 1. 先保留现场：复制当前配置到回滚备份目录
cp -a <TARGET_SERVER_CONF> <BACKUP_DIR>/mingos.after-rollback-trigger

# 2. 只删除本次加入的那一行 include
sed -i '\#include snippets/ming-portfolio-ymai-me.conf;#d' <TARGET_SERVER_CONF>

# 3. 测试并 reload；不要 restart
nginx -t
systemctl reload nginx
```

片段文件与 release 目录**不删除**，留作证据与再次上线使用。

### 11.2 回滚后验证

```bash
node deploy/verify.mjs post --base https://ymai.me --prefix /ming \
  --baseline <BACKUP_DIR>/baseline \
  --expect-index <BACKUP_DIR>/baseline/ming.html
```

回滚后的预期是 `/ming/` 与部署前基线 `ming.html` 字节一致（本次为 21361B，sha256 `564a76ed4b5c…`），根站 `/` 字节不变。若该检查不通过，不要重复 reload，按 §5 恢复整份配置备份。

### 11.3 版本回滚（R1，适用于后续发布）

后续若已有新 release，先把 `current` 指回 `releases/20261103-4b271f0`，再按 §6 复验；不要删除任何 release。

### 11.4 本次现场

配置备份、`nginx -T` 前后 diff、目标 server 配置副本、本次片段副本与部署前基线均保存在服务器内部备份目录（路径不写入公开仓库）。真实路径与备份目录名由运维会话在内部部署记录中保管。

## 12. 根路径切换后的回滚点（2026-11-03）

### 12.1 追加触发条件

除 §1 外，出现以下任一情况立即回滚：

| # | 现象 |
| --- | --- |
| 1 | `https://ymai.me/` 的字节与本次发布产物不一致，或根路径仍返回 Self Space |
| 2 | `/gui/_next/` 的 JS/CSS 再次变成 `text/html`，或 `/gui/space/` 回退成首页 |
| 3 | `/ming`、`/ming/`、`/ming/<路由>` 未 301 到根路径，或出现循环 |
| 4 | `/assets/`、`/media/` 缺失时回退成 SPA HTML 而不是 404 |
| 5 | `/health`、`/api/`、`/api/wechat` 字节或状态改变 |
| 6 | 其他站点（`ymai.fun`、`ymai.love`、`mingos.cn`）出现回归 |

### 12.2 一次性回到子路径方案（推荐）

根路径方案同时改了“server 块里的 `location /`”和“片段内容”，只切 release 不够，必须一起恢复。

```bash
# 1. 保留现场
cp -a <TARGET_SERVER_CONF> <BACKUP_DIR>/mingos.root-failed-<timestamp>
cp -a <SNIPPET_PATH> <BACKUP_DIR>/snippet.root-failed-<timestamp>

# 2. 恢复切换前的 server 块与片段
cp -a <BACKUP_DIR>/mingos.before <TARGET_SERVER_CONF>
cp -a <BACKUP_DIR>/snippet.before <SNIPPET_PATH>

# 3. 校验后切换 release 并 reload（不 restart）
nginx -t
ln -sfn "releases/20261103-4b271f0" <PORTFOLIO_PARENT>/current.next
mv -Tf <PORTFOLIO_PARENT>/current.next <PORTFOLIO_PARENT>/current
systemctl reload nginx
```

预期：`/` 回到 21361B Self Space 首页；`/ming/` 回到 2644B 旧作品集；`/gui/_next/` 回到旧的 HTML 回退状态。这是“回到切换前”，不是“新方案仍可用”，可接受。

### 12.3 只回滚内容（server 与片段保持根路径方案）

若根路径规则正常、只是新构建有问题：

```bash
ln -sfn "releases/<PREVIOUS_RELEASE_ID>" <PORTFOLIO_PARENT>/current.next
mv -Tf <PORTFOLIO_PARENT>/current.next <PORTFOLIO_PARENT>/current
```

无需 reload；验证 `/`、8 条路由与 `/gui/` 资源。

例如 2026-11-03 的发布链是 `20261103-root-0945` → `0956`（修正文案）→ `1040`（统一行尾），当前为 `1040`；内容回滚可切回 `0956` 或 `0945` 并复验，不删除任何 release。

### 12.4 回滚后验证

```bash
node deploy/verify-root.mjs post \
  --base https://ymai.me \
  --baseline <BACKUP_DIR>/baseline-root \
  --expect-index <BACKUP_DIR>/baseline-root/root.html

curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' https://ymai.me/ming/
```

若回到子路径方案，`verify-root.mjs` 的根路径判据会失败，这是预期；此时按 §6 判据确认“回到切换前基线”，不要把“新方案检查失败”当作回滚失败。

### 12.5 本次现场

切换前的 server 块、片段、`nginx -T` 输出与四个入口状态均保存在服务器内部备份目录；新 release 与旧 release 均保留，未删除。

## 13. www 修复与联系通道发布的回滚点（2026-11-03）

### 13.1 追加触发条件

出现以下任一情况，按本节处理：

| # | 现象 |
| --- | --- |
| 1 | `www.ymai.me` 出现 301 循环，或跳到非 `ymai.me` 的地址 |
| 2 | `https://www.ymai.me/` 证书报错、SAN 丢失或续期失败 |
| 3 | 新增 www server 块导致 `nginx -t` 失败或影响根域名 |
| 4 | 联系与合作页三条通道不显示、图片 404，或邮箱 / GitHub Issues 链接不可点 |
| 5 | 根路径、`/gui/`、`/ming` 跳转或 `/health` 出现回归 |

### 13.2 回滚步骤

**只回滚 www（根站内容保持当前版本）**

```bash
# 1. 保留现场
cp -a <WWW_SERVER_CONF> <BACKUP_DIR>/www.failed-<timestamp>

# 2. 删除或停用 www.ymai.me 的 80/443 server 块
#    把 <WWW_SERVER_CONF> 移出 sites-enabled，或恢复为不存在该文件的状态

# 3. 校验并 reload（不 restart）
nginx -t
systemctl reload nginx
```

DNS 侧二选一：

- 保持 `www CNAME ymai.me`：此时 www 不再有专门的跳转规则，可能落到默认站点或其他 server 块，但根域名不受影响；
- 恢复为修复前的 `www CNAME ms8qmmdpyy.coze-dns-01.com`，TTL 600：回到修复前的 Coze 状态。该状态本身不可用，只用于“回到变更前”。

**连同内容一起回滚**

```bash
# 切回根路径上一版发布
ln -sfn "releases/20261103-root-1040" <PORTFOLIO_PARENT>/current.next
mv -Tf <PORTFOLIO_PARENT>/current.next <PORTFOLIO_PARENT>/current
# 不需要 reload nginx
```

`20261103-root-1040` 是联系通道发布前的根路径版本；`20261103-contact-1209`、`20261103-contact-1259`、旧构建资源与所有更早 release 均保留，不删除。

证书无需回滚。新增的 `www.ymai.me` SAN 不影响 `ymai.me`、`ymai.love` 的现有证书匹配；若证书本身出问题，按 §5 恢复证书备份并 reload。

### 13.3 回滚后验证

```bash
node deploy/verify-root.mjs post   --base https://ymai.me   --baseline <BACKUP_DIR>/baseline-contact   --expect-index <BACKUP_DIR>/baseline-contact/root.html

curl --noproxy '*' -sSI https://ymai.me/ | sed -n '1,8p'
curl --noproxy '*' -sSI https://www.ymai.me/ | sed -n '1,8p'
curl --noproxy '*' -sS -L -o /dev/null -w '%{http_code} %{url_effective}
' https://www.ymai.me/cooperation
```

预期：

- 只回滚 www 时，根域名仍为当前版本，`www` 按所选 DNS 方案失败或回到 Coze；
- 连同内容回滚时，根路径回到 2619B / `ac081d8cc5b4`，8 路由一致；
- 无论哪种回滚，`/gui/`、`/ming`、`/health` 都应与回滚前基线一致。

### 13.4 本次现场
